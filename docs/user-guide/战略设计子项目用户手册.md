# 战略设计子项目用户手册

第一次接触战略设计，不需要先学会 DDD，也不需要先写代码。

这本手册带你把一个模糊想法，逐步整理成下游研发团队可以接手的业务方案。全文使用虚构的“客户合同审批”作为例子；示例只用于学习，不要把示例中的业务名称直接写入真实项目。

## 这本手册适合谁

- 产品经理、需求分析师和商务协作者：想把客户问题说清楚。
- 业务专家：需要确认规则、角色、边界和例外情况。
- 第一次使用本模板的人：不知道每个目录和阶段有什么用。
- AI Agent 操作者：需要知道何时检查、何时起草、何时停下来请人确认。

不懂代码也可以读懂前半部分。命令和 Agent 提示词放在相应步骤中，需要时复制即可。

## 看完能做什么

你将能够：

1. 初始化一个战略设计项目实例，并判断自己是否在正确的仓库中。
2. 把“我们想做一个合同审批功能”拆成用户、目标、范围和成功标准。
3. 用通俗语言理解子域、限界上下文、统一语言、Context Map 和不变量。
4. 形成 Spec、页面原型和业务级 Ticket。
5. 判断哪些资料已经可以确认，哪些问题必须停下来问人。
6. 把批准后的 Strategic Design Handoff 交给下游研发团队。

## 先记住一件事：本项目负责什么

战略设计子项目是一个“业务方案工作台”，不是运行时框架，也不是代码仓库。它负责把业务问题收敛为：

| 阶段 | 用大白话说 | 主要产出 |
|---|---|---|
| 入口分诊 | 先确认项目身份和当前进度 | 当前阶段、影响面、缺失项 |
| Discovery | 搞清楚为什么做、为谁做 | 用户、痛点、目标、MVP、非目标 |
| DDD 战略设计 | 划清业务边界和规则 | 子域、限界上下文、统一语言、Context Map、不变量 |
| Spec | 写成大家可以确认的需求 | 用户故事、验收标准、边界条件 |
| 页面原型 | 先把页面和状态想明白 | 页面流、交互说明、状态矩阵、原型 |
| 业务级 Ticket | 拆成下游能接手的业务任务 | 业务级 Ticket、依赖和验收条件 |
| Strategic Design Handoff | 把成果和未决问题交出去 | 版本、证据、下游问题清单 |

本地终点是 Strategic Design Handoff。OpenAPI、Tactical DDD、数据库、代码实现、测试执行和发布属于下游研发项目，不在本子项目内完成。

## 三分钟开始

### 第一步：确认你使用的是项目实例

在项目根目录打开 `yss-project.yaml`：

| 配置 | 含义 | 下一步 |
|---|---|---|
| `repository_mode: project-instance` | 这是一个真实业务项目实例 | 可以记录真实项目资料 |
| `repository_mode: template-source` | 这是模板源 | 只能维护模板，不能写真实产品方案 |
| 文件缺失或值不合法 | 项目身份不清楚 | 先停止，做迁移检查 |

### 第二步：初始化（还没有项目时）

在准备存放项目的父目录运行：

```bash
npx create-yss-harness-design@latest
```

按提示填写项目名称、业务领域和目标目录。初始化完成后，至少应看到 `yss-project.yaml`、`CONTEXT.md`、`AGENTS.md` 和 `docs/`。

CLI 的完整参数、接管已有目录和更新模板，请看[外部命令行工具实践指南](./外部命令行工具实践指南.md)。

### 第三步：只读检查

进入项目实例根目录，把下面提示词发给 Agent：

```text
使用 yss-strategic-design，以 route 模式检查“客户合同审批”功能。
请先读取 yss-project.yaml、CONTEXT.md 和当前已有资料。
本轮只读，不要修改文件。请用普通话告诉我：
1. 当前处于哪个战略设计阶段；
2. 已有资料哪些仍然有效；
3. 缺少哪些资料或人工决定；
4. 下一步只做哪一件事。
正式 ID 放在普通话解释后面。
```

`route` 只检查、不写文件。第一次使用时优先选它；确认范围后才使用 `orchestrate` 推进。

## 一条路线看懂完整过程

下面用“客户合同审批”走一遍。假设公司希望让销售提交合同，由法务和财务按规则审批，审批通过后才能签约。

### 1. 入口分诊：先判断从哪里开始

**你要回答**：这是哪个项目？已有资料在哪？这次改变页面、业务规则还是跨团队协作？

**建议做法**：让 Agent 只读检查，不要因为目录里有一个文件就假设阶段已经完成。阶段是否完成，要看内容、批准记录和资料是否仍然新鲜。

**完成信号**：你知道当前阶段、影响面、最近可信资料和下一步；如果身份不合法，应停在这里。

### 2. Discovery：说明为什么做

先不要讨论数据库或接口，先把业务问题说清楚：

| 问题 | “客户合同审批”示例 |
|---|---|
| 谁遇到问题 | 销售提交合同后，不知道审批到哪一步 |
| 当前痛点 | 通过邮件来回确认，容易漏审或重复审批 |
| 想达到什么结果 | 销售能提交并查看进度，审批人能处理自己的待办 |
| MVP 做什么 | 提交、退回、审批、查看状态和审批记录 |
| 本次不做什么 | 不做自动定价、不做电子签章、不做跨公司审批 |
| 怎样算成功 | 合同状态清楚，审批人不会错过待办，退回原因可追溯 |

把已确认事实、仍待确认的问题和明确非目标分开写。需要外部市场或竞品事实时，先做研究并记录来源；不要让 Agent 猜答案。

### 3. DDD 战略设计：划清业务边界

DDD 可以先理解为“用业务语言分工和画边界”。不要求一开始就画出完美模型，先把下面五个概念说清楚即可。

| 概念 | 白话解释 | 合同审批例子 | 常见误区 |
|---|---|---|---|
| 子域 | 业务中相对完整的一块工作 | 合同提交、合同审批、合同归档 | 按部门名称机械切分；一个部门可能包含多个子域 |
| 限界上下文 | 一块范围内，词语和规则含义保持一致 | “审批上下文”只关心审批人、审批意见和审批状态 | 把所有功能放进一个“大上下文” |
| 统一语言 | 团队对同一个词使用同一个含义 | “退回”表示审批人要求补充材料，不等于“拒绝” | 同一词在不同文档里含义不同 |
| Context Map | 上下文之间如何合作 | 合同提交把待审批合同交给审批上下文；审批结果回传合同上下文 | 把它当成数据库表关系图 |
| 不变量 | 无论发生什么都不能违反的规则 | 已通过的合同不能被直接改成草稿；审批必须留下操作人和时间 | 把每个页面按钮都写成不变量 |

建议在 `CONTEXT.md` 登记稳定业务词汇，例如“合同”“审批”“退回”“拒绝”“审批记录”，并为每个词确认 PascalCase 英文标识。词汇未确认前，不要让它进入 Spec 或代码。

**完成信号**：业务人员能用自己的话解释边界；跨上下文的关系、关键场景和不变量没有明显冲突；有争议的地方记录责任人和后续决定，而不是假装已经定案。

### 4. Spec：把方案写成可确认的需求

Spec 不是技术设计，而是“用户要完成什么，以及怎样判断完成”。一个最小用户故事可以写成：

> 作为销售，我希望提交客户合同并看到审批进度，以便知道何时可以继续签约。

验收标准要写结果，不只写按钮：

- 提交成功后，合同状态变为“待审批”，并显示当前审批节点。
- 审批人只能处理分配给自己的待办。
- 退回必须填写原因，销售可以看到原因并重新提交。
- 每次审批都记录操作人、时间、动作和意见。

同时写清空态、错误、重复提交、取消和权限边界。Spec 初稿应保持 `ready-for-human`，需要指定人员确认后才能作为下游输入。

### 5. 页面原型：先验证使用过程

至少画出三条路径：销售提交、审批人处理、销售查看结果。每条路径都要考虑：加载中、没有数据、提交失败、退回、审批通过和无权访问。

原型的目的不是追求漂亮，而是尽早发现“状态说不清”“下一步找不到”“退回后无法继续”等问题。原型确认记录和状态矩阵应与 Spec 保持一致；出现新业务状态时回到 Spec 和 DDD 设计重新确认。

### 6. 业务级 Ticket：交给下游研发

Ticket 按用户可验证的业务路径拆分，例如：

1. 销售提交合同并查看待审批状态。
2. 审批人查看自己的待办并批准或退回。
3. 销售查看退回原因并重新提交。
4. 查看完整审批记录。

每个 Ticket 都要有用户价值、验收标准、依赖、风险、回滚考虑和验证方式。不要只拆成“前端 Ticket、后端 Ticket、数据库 Ticket”；那会让一个业务行为被切碎，难以独立验收。

### 7. Strategic Design Handoff：把成果交出去

交付前检查：

- Spec、原型、业务级 Ticket 和 DDD 战略设计引用的是同一版本。
- 关键术语已经登记，冲突和未决问题有负责人。
- 下游需要决定的内容单独列出，例如聚合边界、并发策略、API 细节和数据存储。
- 交付包包含来源 digest、批准记录和下游问题清单。

完成交付后，下游研发团队使用 Tactical DDD 流程继续细化。不要在本项目里擅自补写 OpenAPI、代码或实现结论。

## 两种推进方式

| 模式 | 普通话解释 | 是否写文件 | 适用时机 |
|---|---|---|---|
| `route` | 看现状和下一步 | 否 | 第一次检查、范围变化、怀疑资料过期 |
| `orchestrate` | 按已确认范围推进 | 是 | 允许补文档且输入已明确 |
| `resume` | 中断后重新核对再继续 | 是 | 会签完成、补齐资料后 |
| `audit` | 独立检查是否漏项 | 否 | 交付前或怀疑状态不一致 |

推进提示词示例：

```text
继续使用 yss-strategic-design，以 orchestrate 模式推进“客户合同审批”。
只处理当前已确认范围；遇到需要人工决定、资料过期或发现新影响时停下。
每完成一步，请告诉我改了什么、证据在哪里、下一步是什么。
```

## 常见问题

| 问题 | 简单回答 |
|---|---|
| 我不会 DDD，能不能直接写 Spec？ | 可以先写 Discovery，但涉及边界、术语或核心规则时，先补 DDD 战略设计，避免后面反复改。 |
| 目录里已经有 Spec，是否说明阶段完成？ | 不一定。还要检查内容是否完整、是否批准、上游是否发生变化。 |
| 可以让 Agent 直接决定审批规则吗？ | 不可以。Agent 可以整理问题和提出选项，业务规则必须由业务负责人确认。 |
| 什么时候需要 OpenAPI？ | 本子项目只记录 API 影响和交接问题；OpenAPI Draft / Freeze 由下游研发 profile 负责。 |
| 为什么不能直接开始写代码？ | 因为本模板的本地终点是业务交接。代码实现需要批准的上游输入和下游工程合同。 |
| `ready-for-human` 是不是可以开发？ | 不是。它表示仍需会签或人工确认；只有下游垂直切片合同满足条件后才可能进入 `ready-for-agent`。 |
| 示例中的“客户合同审批”可以复制到项目吗？ | 不可以。它只是教学示例；真实项目必须使用已确认的业务词汇和英文标识。 |

## 自检清单

在把成果交给下游前，逐项确认：

- [ ] 我能说清项目身份和当前战略设计阶段。
- [ ] 用户、痛点、目标、MVP、非目标和成功标准已分开记录。
- [ ] 关键业务词汇已在 `CONTEXT.md` 确认。
- [ ] 子域、限界上下文、Context Map、场景和不变量没有互相矛盾。
- [ ] Spec 有用户故事、验收标准、边界和异常情况。
- [ ] 原型覆盖主流程和关键状态，并有人工确认记录。
- [ ] 业务级 Ticket 可以按用户路径独立验证。
- [ ] Strategic Design Handoff 引用了当前版本、批准记录和下游问题清单。
- [ ] 没有把 OpenAPI、Tactical DDD、代码或发布结论冒充本项目产出。
