# 业务方案设计子项目用户手册

这本手册面向产品经理、需求分析师、商务协作者和业务专家。你不需要先学习软件建模或编程，只需要能讲清真实业务怎样发生、由谁负责、遵守什么规则。

全文使用虚构的“客户合同审批”作为例子；示例只用于学习，不要把示例中的业务名称直接写入真实项目。

## 看完能做什么

你将能够：

1. 判断自己是否在正确的项目实例中；
2. 把模糊想法整理成用户、目标、范围和成功标准；
3. 用业务故事串起参与者、动作、资料和结果；
4. 划清业务责任区、协作关系和不可违反的业务规则；
5. 形成 Spec、页面原型和业务级 Ticket；
6. 把已确认的业务方案和研发待决问题交给下游团队。

## 一条主线看懂完整过程

`机会与目标 → 业务故事 → 责任与交接 → 规则、例子与疑问 → 可验收需求 → 页面验证 → 业务任务 → 交接研发`

| 阶段 | 用大白话说 | 主要产出 |
|---|---|---|
| 入口分诊 | 先确认项目身份和当前进度 | 当前阶段、影响面、缺失项 |
| 机会与目标 | 搞清楚为什么做、为谁做 | 用户、痛点、目标、MVP、非目标 |
| 业务故事 | 按时间讲清业务怎样发生 | 参与者、动作、业务资料、结果 |
| 业务边界与协作 | 说明谁负责什么、怎样交接 | 业务板块、业务责任区、协作关系 |
| 规则、例子与疑问 | 用具体例子校准规则和例外 | 规则、正反例、未决问题、责任人 |
| Spec | 写成大家可以确认的需求 | 用户故事、验收标准、边界条件 |
| 页面验证 | 提前发现流程和状态问题 | 页面流、状态矩阵、原型和确认记录 |
| 业务级 Ticket | 拆成下游能接手的业务任务 | 业务 Ticket、依赖和验收条件 |
| 业务方案交接 | 把成果和未决问题交出去 | 当前版本、证据、研发待决问题 |

本项目是“业务方案工作台”，不是代码仓库。OpenAPI、数据库、技术模型、生产代码、测试执行和发布由下游研发项目负责。

## 三分钟开始

### 第一步：确认项目身份

在项目根目录打开 `yss-project.yaml`：

| 配置 | 含义 | 下一步 |
|---|---|---|
| `repository_mode: project-instance` | 这是真实业务项目实例 | 可以记录真实项目资料 |
| `repository_mode: template-source` | 这是模板源 | 只能维护模板，不能写真实产品方案 |
| 文件缺失或值不合法 | 项目身份不清楚 | 停止并做迁移检查 |

### 第二步：初始化

在准备存放项目的父目录运行：

```bash
npx create-yss-harness-design@latest
```

初始化完成后，至少应看到 `yss-project.yaml`、`CONTEXT.md`、`AGENTS.md` 和 `docs/`。

### 第三步：先做只读检查

```text
使用 yss-strategic-design，以 route 模式检查“客户合同审批”功能。
请先读取 yss-project.yaml、CONTEXT.md 和已有资料。
本轮只读，不要修改文件。请用普通话告诉我：
1. 现在进行到哪一步；
2. 哪些资料仍然有效；
3. 缺少哪些事实或人工决定；
4. 下一步只做哪一件事。
正式 ID 放在普通话解释之后。
```

`route` 只检查、不写文件。第一次使用时优先选择它；确认范围后再使用 `orchestrate` 推进。

## 默认由 Agent 问六个问题

业务角色不需要直接填写内部合同。Agent 应依次问清：

1. 谁遇到了什么问题，想得到什么结果？
2. 事情通常怎样一步步发生？
3. 每一步由谁负责，结果交给谁？
4. 有哪些规则、例外和仍待确认的问题？
5. 哪一小段可以独立交付并让用户得到结果？
6. 用哪些例子和证据证明结果正确？

Agent 可以建议答案、整理材料和发现矛盾，但业务规则、范围和优先级必须由相应负责人确认。

## 用“客户合同审批”走一遍

### 1. 机会与目标

| 问题 | 示例 |
|---|---|
| 谁遇到问题 | 销售提交合同后，不知道审批到哪一步 |
| 当前痛点 | 通过邮件来回确认，容易漏审或重复审批 |
| 想达到什么结果 | 销售能提交并查看进度，审批人能处理自己的待办 |
| MVP 做什么 | 提交、退回、审批、查看状态和审批记录 |
| 本次不做什么 | 不做自动定价、电子签章和跨公司审批 |
| 怎样算成功 | 状态清楚、待办不遗漏、退回原因可追溯 |

把事实、假设、未决问题和明确非目标分开写。需要外部事实时先研究并保留来源，不让 Agent 猜答案。

### 2. 业务故事

先讲最常见的顺利过程，每一步使用“谁—做什么—对什么—产生什么结果”：

1. 销售填写合同资料并提交；
2. 系统把合同交给相应审批人；
3. 审批人检查合同并批准或退回；
4. 销售看到结果；
5. 通过的合同进入后续签约，退回的合同补充后重新提交。

讲完顺利过程，再补充失败、取消、超时、重复操作和资料不完整等情况。

### 3. 业务边界与协作

| 业务说法 | 要回答的问题 | 示例 |
|---|---|---|
| 业务板块 | 哪几块工作各自有完整目标 | 合同准备、合同审批、合同归档 |
| 业务责任区 | 哪套词和规则在什么范围内成立，由谁负责 | 审批责任区负责审批人、意见和审批状态 |
| 统一业务词汇 | 同一个词在当前范围内是什么意思 | “退回”是要求补材料，不等于“拒绝” |
| 协作与交接关系 | 谁提供信息或规则，谁使用，口径不同时谁转换 | 合同准备把待审批资料交给审批责任区 |
| 不可违反的业务规则 | 无论走哪条路径都不能破坏什么 | 已通过合同不能直接改回草稿；审批必须留痕 |

不要按部门、菜单、数据库表或现有系统名称机械分块。先从真实业务故事、规则责任和失败路径中找边界。

需要判断投入重点时，Agent 不应要求业务人员选择抽象分类，而应询问：

- 这块工作是否直接决定关键业务结果？
- 是否存在只有本组织才有的独特规则？
- 是否属于不可缺少的支撑工作？
- 是否可以直接复用成熟能力或外购？

Agent 根据回答提出“重点业务、必要支撑、通用能力”的建议，再由业务负责人确认。

稳定词汇登记在项目根目录唯一的 `CONTEXT.md`。业务人员确认中文名称、含义、易混淆叫法和适用业务责任区；PascalCase 标识及 `<ContextId>/<EnglishIdentifier>` 引用由 Agent 维护。候选词汇未确认前留在问题清单中。

### 4. 规则、例子与疑问

每条规则至少配一个普通例子，关键规则再补边界或失败例子：

| 规则 | 普通例子 | 边界 / 失败例子 | 未决问题 |
|---|---|---|---|
| 退回必须填写原因 | 法务退回并说明缺少附件 | 原因为空时不能提交 | 原因是否限制长度？ |
| 只能处理自己的待办 | 法务处理分配给自己的合同 | 打开他人待办时不能操作 | 是否允许管理员代办？ |

未决问题必须写负责人和最晚确认点，不能因为不知道答案就让 Agent 自动决定。

### 5. Spec 与页面验证

Spec 记录“用户要完成什么，以及怎样判断完成”，例如：

> 作为销售，我希望提交客户合同并看到审批进度，以便知道何时可以继续签约。

验收标准描述可观察结果，不只描述按钮。页面验证至少覆盖销售提交、审批人处理、销售查看结果，以及加载、空态、失败、退回、通过和无权访问等状态。出现新规则或新状态时，回到业务故事和规则部分重新确认。

### 6. 业务级 Ticket

按用户可以验证的业务结果拆分：

1. 销售提交合同并看到待审批状态；
2. 审批人查看自己的待办并批准或退回；
3. 销售查看退回原因并重新提交；
4. 用户查看完整审批记录。

不要只拆成“前端、后端、数据库”三类任务。每个 Ticket 都应包含用户价值、验收标准、依赖、风险和验证方式。

### 7. 业务方案交接

交付前检查：

- 业务边界与规则设计、方案决策包、Spec、原型和业务级 Ticket 引用同一版本；
- 关键业务词汇已经确认，冲突和未决问题有负责人；
- 研发需要继续决定的内容单独列出，例如并发策略、API 细节和数据存储；
- 交接包包含来源 digest、批准记录、目标仓词汇对账要求和研发待决问题；
- 本项目没有越界生成 OpenAPI、数据库设计、代码或发布结论。

下游团队接手后，先把交接包中的词汇变化对账到目标仓库，再开展技术设计。

## 四种推进方式

| 模式 | 普通话解释 | 是否写文件 | 适用时机 |
|---|---|---|---|
| `route` | 看现状和下一步 | 否 | 第一次检查、范围变化、怀疑资料过期 |
| `orchestrate` | 按已确认范围推进 | 是 | 允许补文档且输入已明确 |
| `resume` | 中断后重新核对再继续 | 是 | 会签完成、资料补齐后 |
| `audit` | 独立检查是否漏项 | 否 | 交接前或怀疑状态不一致 |
