# 战略设计子项目用户手册

本指南面向产品经理、需求分析师、商务协作者及项目使用者。当前家族为 `harness.business-ddd-strategy-handoff`。从用户问题形成业务方案及战略交接；不在本仓冻结工程 API、生成后端/前端工程或实施代码。

## 先选路线

| 你的任务 | 选择 | 创建与更新入口 |
|---|---|---|
| 从想法到发布，统一管理整个业务切片 | 综合模板 `yss-spec-project-template` | `create-yss-spec`：初始化、attach、sync |
| 澄清业务、Spec、原型并交接研发 | 战略模板 `yss-harness-design-agent` | `create-yss-harness-design`：初始化；无 attach/sync |
| 接收已批准上游，统一组织研发 | 通用研发模板 `yss-harness-dev-agent` | `create-yss-harness-dev`：初始化、attach、sync |
| 独立团队承担后端并输出交付包 | 后端模板 `yss-harness-backend-agent` | 仓内 `scripts/instantiate-harness`；仅新目录 |
| 接收战略及后端交付，承担前端 | 前端模板 `yss-harness-frontend-agent` | 仓内 `scripts/instantiate-harness`；仅新目录 |

通用研发和前后端专职是可选择的组织方式，不要求现有通用项目迁移。采用专职路线时，登记一个统一管理方汇总业务切片，不能把两端自报完成直接相加当作业务验收。

## 创建并检查

在已发布渠道初始化：

```bash
npm create yss-harness-design@latest
```

也可执行 `npx create-yss-harness-design@latest --project-name "设备借用" --business-domain "内部设备管理" --target-dir ./equipment-project`。目标优先新目录。

本手册描述 GitHub 当前实现。`@latest` 指 npm 已发布版本，其模板快照可能落后于 GitHub。使用前运行 `npm view <包名> version` 核对；包名占位符须替换。未发布的候选不能用对应的 npm 版本号直接安装。

要使用尚未发布的手册版本，从对应 CLI 的 GitHub 固定提交检出，按该仓 README 的候选包步骤构建；检查 `template.snapshot.json` 的 `templateCommit` 与包版本。CLI 初始化使用包内快照，不会实时拉取最新模板。不同家族的快照和版本号分别记录。

初始化完成后进入目标目录，核对 `yss-project.yaml` 的 project-instance 身份、家族 metadata、根 CONTEXT.md 和 profile；从本地 [索引](用户手册索引.md) 开始。运行时代码进入登记的实现仓，不写回模板源。

## 第一次让 Agent 工作

先在生成的项目实例中打开 Agent，发送：

```text
请先只读检查 yss-project.yaml、根 CONTEXT.md、AGENTS.md，以及存在的 harness-profile.yaml。
告诉我本仓职责、当前可信阶段、上游输入、缺失证据和下一步。
发现身份不合法或输入过期时停止并给出恢复办法；先不要写代码。
```

成功时应得到明确的仓库身份和可追踪输入，不是泛泛的开发计划。`template-source` 只能维护可复用模板；真实业务必须在 `project-instance` 中记录。真实业务词汇只登记在实例根 `CONTEXT.md`，不复制本手册示例当作已确认事实。

## 用户确认什么

| 看到的材料 | 你需要判断 | 确认后的边界 |
|---|---|---|
| 目标、范围、规则及反例 | 是否符合业务、哪些不做 | 允许继续设计；不自动批准实现 |
| 页面流程、状态与视觉基线 | 成功、失败、权限和恢复是否完整 | 形成对应产品设计输入 |
| 工程/接口/脚手架方案 | 责任、兼容、数据和回滚是否可接受 | 按本仓角色政策完成适用会签 |
| 当前 Slice Contract | 写哪些仓库与路径、怎么验收 | 必要门禁通过后才能实施 |
| 本轮验证和发布方案 | 覆盖、风险、回滚和交付范围 | 发布及外部承诺仍需生物人 |

具体批准身份和门禁以本仓 `docs/agents/digital-human-roles.yaml`、`docs/process/lifecycle-registry.yaml` 为准。Agent 起草、自报通过或文件中写 `approved` 均不能代替真实批准。`ready-for-human` 是待指定会签；只有可直接实施的切片才使用 `ready-for-agent`。

## 本仓操作路线

`机会与目标 → 业务故事与责任边界 → 规则/反例 → Spec → 所需原型与视觉基线 → 业务级 Ticket → 批准交接`

```text
请按本仓战略流程澄清设备借用的目标、参与者、范围和规则。
按依赖逐轮提问，确认后才起草方案；整理页面状态、未决事项和研发交接证据。
不要开始工程 API、数据库或代码实现。
```

1. 收集真实用户问题、目标与限制，区分已确认决定和待确认假设。
2. 核对根词汇与业务边界，形成 Spec；有 UI 时准备页面、状态和当前视觉基线。
3. 按本仓政策完成用户决定与适用批准，准备业务级 Ticket 及交接描述。
4. 导出完整战略包，独立验包并记录版本摘要；把研发待决项和影响范围交给下游。

预期每步给出实际输入、产物路径、当前版本、阻塞与下一步；详情跟随本地 [设备借用案例](设备借用贯穿案例.md)。战略交接完成不等于产品发布。下游需要重新对账并准备其工程契约。

## 升级与恢复

战略实例没有自动 sync 或跨 profile 原地迁移。先用同家族新目录对比受管资产，记录迁移范围和回滚点；迁移后复验输入、词汇、合同及验证脚本，保留旧目录。

五家族由 `.yss-template.json`、`.yss-harness-design.json`、`.yss-harness-dev.json`、`.yss-harness-backend.json`、`.yss-harness-frontend.json` 及 profile 判定。不得删除或伪造 metadata 来切换家族。

异族、多重身份、损坏 metadata、未知或矛盾 profile 会在规划/写入前被拒绝；`--force` 不能绕过，`--dry-run` 同样检查。只有在身份及路径检查通过后，force 才按该命令的覆盖语义生效。遇到拒绝先核对所用家族和目标路径，保留原目录，不用战略 init 强制替代升级。

## 查错与退出

包摘要失败回交源方；规则冲突回交战略方；接口和环境缺口回交后端；前端视觉/交互差异按当前基线修正。每次恢复重验受影响输入，不复用旧成功结论。

“完成”必须附本轮命令、时间、退出码、日志及未覆盖风险；实现者不得独立审查自己的工作。角色和门禁以 [profile](../process/harness-profile.yaml)、本仓 lifecycle-registry.yaml 和 digital-human-roles.yaml 为准。

维护者操作见 [维护与兼容](规格与任务迁移指南.md)，日常协作见 [最佳实践](生命周期最佳实践.md)。

## 用业务问题检查每次交接

| 工作 | 先回答的问题 | 要给下游的材料 |
|---|---|---|
| 机会与目标 | 谁遇到了什么问题 | 目标、限制与成功标准 |
| 业务故事 | 事情通常怎样一步步发生 | 参与者、动作与结果 |
| 业务责任区与协作 | 每一步由谁负责 | 责任、交接与未决项 |
| 规则与例子 | 有哪些规则、例外 | 规则、正常和失败例子 |
| Spec 与业务级 Ticket | 哪一小段可以独立交付 | 可验收范围与依赖 |
| 页面验证与业务方案交接 | 用哪些例子和证据证明结果正确 | 页面状态、批准和版本证据 |

这些步骤只是导航视图，不成为新的事实来源；阶段与批准政策仍由本仓注册表和角色表定义。
